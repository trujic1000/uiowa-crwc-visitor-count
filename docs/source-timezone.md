# Source timestamp investigation

Checked September 18, 2026. This investigation used public sources and made no database changes.

## Adopted assumption — September 23, 2026

The user confirmed Central time as a reasonable assumption and delegated the winter-offset choice. We adopt **America/Chicago**, with UTC−05 during daylight saving and UTC−06 during standard time, under policy `assumed-america-chicago-v1`. This supersedes the earlier decision to defer normalization; it is still not a vendor-verified contract.

`src/source-time.ts` uses Temporal named-zone conversion with `disambiguation: 'reject'`. Nonexistent spring-forward times, ambiguous fall-back times, invalid timestamps, and instants later than first retrieval remain NULL. Those records stay available but are excluded from measurement-time charts and labelled unresolved. Normalized UTC values use millisecond precision; full raw source precision is preserved. Existing raw-timestamp uniqueness is unchanged: a repeated fall-back wall time may still collide, but it will not be assigned a guessed UTC instant. Fetch logs retain evidence.

The collector writes `measured_at` for new rows. The dashboard uses measurement time for chart points and Today filtering, with an explicit Chicago-assumed label; first-observed times remain separately visible. Old local snapshots normalize on read until refreshed. Fetch/collector health continues to use UTC retrieval timestamps.

Historical backfill is generated by `scripts/prepare-timezone-backfill.ts` from a Wrangler JSON snapshot. It only fills NULL values, guards the original ID/raw/fetch values, and creates a matching rollback file. The September 23 dry run found 990 normalizable rows and no unresolved timestamps. Apply/replay/rollback were verified against the existing schema. The backfill was then applied remotely and all 990 values were rechecked against this policy, with raw and fetched timestamps unchanged. The collector and dashboard updates are deployed. No schema migration is necessary. Artifacts are in ignored `work/timezone/`; keep the before snapshot and rollback until comfortable with the assumption.

## Earlier investigation (September 18)

## Finding

**The public interface does not specify the timestamp timezone.** `America/Chicago` is a plausible interpretation, but neither the API response nor the widget establishes that contract. Keep `source_measured_at_raw` intact and `measured_at` NULL until normalization is justified. The dashboard can show the source's literal date and time with a timezone-unverified label in the meantime; collector fetch times are independently known UTC instants.

## Verified evidence

- The [University of Iowa facility page](https://recserv.uiowa.edu/campus-recreation-wellness-center) links the [Connect2 live-count widget](https://www.connect2mycloud.com/Widgets/Data/locationCount?type=bar&key=8c72a6a7-d6ee-4520-bc3a-52215462ac23).
- Inspection of that widget's inline JavaScript shows it fetches `GetCountsByAccount`, constructs `new Date(countLocation.LastUpdatedDateAndTime)`, then formats using local getters such as `getHours()` and `getMinutes()`. There is no explicit timezone or UTC conversion in that display path. Thus it is not evidence that the source has already normalized timestamps.
- ECMAScript treats an offset-free date-time string as local time. Parsing it and using local getters generally reproduces its wall-clock digits, even on computers in different timezones; DST gaps can also change those digits. The widget's rendered clock alone cannot verify the original timezone. See [ECMAScript Date.parse](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-date.parse).
- A fresh [public API response](https://goboardapi.azurewebsites.net/api/FacilityCount/GetCountsByAccount?AccountAPIKey=8c72a6a7-d6ee-4520-bc3a-52215462ac23), checked at `2026-09-18T13:29:02Z`, contained 11 CRWC rows. Their top-level fields included no timezone/offset metadata, and their measurement timestamps had no offset. For example, the first-floor reading was `2026-09-18T07:47:30.74`, count 11, `IsClosed = false` (not proof of current opening hours). Competition Pool, Rec Pool, and Climbing Wall were closed with a retained timestamp of `2026-09-17T22:54:22.82`. These are observations from that response, not a permanent API guarantee.
- The vendor's [Counts documentation](https://www.connect2concepts.com/features-pages/count) describes utilization counts and a public widget/API, but does not document timestamp timezone semantics.

## Interpretation and remaining verification

The first-floor example would be about 42 minutes old under Chicago daylight time, versus about 5 hours 42 minutes under UTC. That makes Chicago plausible; a single snapshot cannot distinguish timezone from delayed publication. Per-measurement first-seen lags over the collected history provide stronger evidence, especially newly published updates bracketed by two successful polls. Compare candidate interpretations against those brackets, and separate retained overnight/closed readings from new updates.

Even a strong five-hour offset match during September cannot establish whether the vendor follows Chicago daylight saving rules or uses a fixed offset. A documented vendor/institution contract, explicit source offset metadata, or observations across a seasonal transition would resolve that further question. No message to the vendor or university was sent.

September 18 D1 analysis of all 496 distinct rows found no negative first-seen lags when interpreting source timestamps as Chicago daylight time. Per-area median lags were 3.9–6.2 minutes, with minima of 0.1–1.0 minutes, consistent with ten-minute polling. This supports UTC−05 for the sample but does not prove year-round Chicago rules. See [data readiness](data-readiness.md); local calculation output is `work/readiness/analysis.json`. No normalized values were changed.

## Proposed normalization policy

When there is sufficient evidence to adopt an IANA zone, normalize through an explicit named-zone conversion and record its provenance. Never append `Z` to the raw value or depend on the host machine's timezone. Review a dry-run backfill before changing production values.

- Unique local time: convert using the zone's rules for that date, retaining the raw source value.
- Repeated fall-back time: keep normalized time unknown unless independent evidence uniquely identifies the occurrence. Do not silently choose the earlier or later hour.
- Nonexistent spring-forward time: keep normalized time unknown and flag it for review. Do not silently shift the time forward.
- Impossible future instant or unexplained clock regression: flag for review rather than correcting the source silently.

An explicit `disambiguation: 'reject'` conversion supports rejecting both DST ambiguity cases; see the [Temporal timezone documentation](https://tc39.es/proposal-temporal/docs/timezone.html). This is a proposed behavior, not a dependency choice or an implementation in the collector.

The existing unique key uses location and raw timestamp. If a fall-back hour repeats the exact same raw timestamp, it cannot preserve both instants as separate measurements; the fetch log remains the evidence. Review that identity policy before a DST transition rather than assuming UTC backfilling alone resolves it.
